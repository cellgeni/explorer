## Summary

The baseline on the new main is green, and the earlier findings are unchanged: the 12 failing repros still fail the same way, the recording repros still pass, and none of the code or documentation lines the findings cite was edited (`evidence/addendum/anchors.tsv`).

The new code is well tested (82–100% line coverage for the new and changed modules) and mostly correct. The table-row mapping for sections, the shared table read and its release, the `geneSets=` escaping, the manifest and schema keys, and the documented collection file form all check out. The review adds four findings: one P1, one P2 and two P3.

- **EXP-039 (P1):** each time the 3D cell view opens, it keeps a WebGL context. On the 16th open, Chromium drops its oldest context, which is the 2D view's. The 2D view then draws nothing, with no error, until the page is reloaded. The 3D section stack, the 3D volume view and side-by-side panels mount their viewers the same way. This is EXP-011's leak, here reaching the canvas in use.
- **EXP-040 (P2):** when a table is split into sections and has both an obs `z_um` column and a third obsm `spatial` column that varies within a section, the 3D stack adds the two. A cell at 101 µm is drawn and labelled at 201 µm.
- **EXP-041 (P3):** a `section` column of whole numbers, which is how anndata stores integer IDs, is not found when `collection=` splits a table without naming a column, and `Open N Sections` is never offered for it. Naming the column (`#obs.section`) works.
- **EXP-042 (P3):** the 3D stack and the 3D cell view leave deck.gl's focusable root inside an `aria-hidden` element (axe `aria-hidden-focus`, serious). This was already present at `6a9a736` for the stack.

### EXP-039 Opening a 3D view 16 times loses the 2D view's WebGL context

- **Severity:** P1. **Confidence:** confirmed by execution for the 3D cell view; static proof for the other viewers. **Status:** new. **Category:** reliability.
- **Affected and trigger:** the 2D view of any dataset, after 16 openings of a viewer that mounts its own deck.gl canvas while the 2D view stays mounted, with no dataset load in between. Executed for the 3D cell view, on an `.h5ad` with a third obsm `spatial` column; AnnData Zarr stores open the same view. The 3D section stack (`src/App.tsx:5092`), the 3D volume view (`src/App.tsx:5047`, `src/components/VolumeViewer.tsx:118`) and side-by-side panels (`src/App.tsx:5078`, `src/features/collection/LinkedSections.tsx:225`) mount their canvases the same way; those three existed at `6a9a736`.
- **Expected:** `2D View` "returns to the 2D view, which kept its place" (`docs/ui-reference.md`, 3D Cell View). Opening and closing a view should not use up a browser resource.
- **Actual:**
  - Each open mounts `SectionStackViewer`'s `DeckGL` (`src/features/collection/SectionStackViewer.tsx:70,234`; `src/App.tsx:5056`), and each close unmounts it.
  - As EXP-011 established, `@deck.gl/react` finalizes the Deck but never destroys its WebGL device, which stays referenced, so every closed view keeps a live context.
  - Chromium allows 16 live WebGL contexts per page. On the 16th open it logs "Too many active WebGL contexts. Oldest context will be lost." The oldest context is the 2D view's, created when the dataset loaded.
  - From then on the 2D view draws no cells. The minimap, scale bar and coordinate readout still update, no error is shown, and zooming does not bring the cells back.
- **Reproduction:** `evidence/addendum/cell-view-contexts.add.mjs` opens `cells3d.h5ad` (3,000 cells), switches Cells › `View` to `3D` and back 20 times, and counts the WebGL contexts created and lost.
- **Evidence:** `evidence/addendum/cell-view-contexts.json` and `cell-view-contexts-gc.json`, plus screenshots `cell-view-contexts-before.png` and `cell-view-contexts-after-zoom.png`.
  - After toggle 15: 16 contexts created and none lost.
  - After toggle 16: 17 created and 1 lost, and the lost one's canvas is still on the page. `isContextLost()` is true for the 2D view's canvas.
  - After toggle 20: 21 created and 5 lost.
  - Forcing a garbage collection after every close gives the same counts, so the contexts are retained, not waiting to be collected.
- **Impact:** a user who compares the 2D and 3D views of one dataset loses the 2D view without warning and must reload. Other 3D or side-by-side openings since the last load count towards the same 16.
- **Severity rationale:** EXP-011 was rated P2 because no lost context had been shown, and was to become P1 if one was. Here the context in use is lost at 3,000 cells, and the threshold does not depend on dataset size. Dataset switches did not show this, because each load creates the 2D view's context anew, so it is never the oldest.
- **Existing reference:** EXP-011 (same retaining path; T11).
- **Smallest correction:** when a viewer's canvas unmounts, destroy its device and lose its context: call `device.destroy()` and `WEBGL_lose_context.loseContext()`. Put this in one wrapper used by `SectionStackViewer`, `VolumeViewer`, `LinkedSections` and `ViewerCore`. Keeping a single Deck mounted, T11's preferred option, does not cover these viewers.
- **Acceptance:** `cell-view-contexts.add.mjs` reports at most 2 contexts not lost after 20 toggles, `lostOnPage` 0, and the 2D view's context not lost. The same holds for 20 openings of the 3D section stack.
- **Remaining uncertainty:** Firefox and Safari were not run; their context limits differ. The stack, volume view and side-by-side panels were not executed. A real GPU was not used, but the limit is a browser constant.

### EXP-040 A split table's sections are stacked at section z plus the cells' table z

- **Severity:** P2. **Confidence:** confirmed by execution (in-memory table through the real split, section reads and stack matrix). **Status:** new. **Category:** correctness.
- **Affected and trigger:** AnnData tables opened with `collection=<table>` (or `#obs.<column>`) that have both a numeric obs column named `z` or `z_…` and a third obsm `spatial` column that varies within a section. That is a table that records each section's depth and each cell's own z in the table's frame.
- **Expected:** the sections "share the table's obsm coordinates" (`docs/dataset-collections.md`, Sections Of One Table). A cell should be drawn and labelled at the z it has in the table, as the whole table's 3D cell view does.
- **Actual:**
  - `sections()` gives each section the z of the obs column it shares (`src/datasets/h5adDataset.ts:1172-1180`).
  - `withSection` keeps the cells' own z whenever it varies within the section (`h5adDataset.ts:1801`, `sectionDepths` at 1917).
  - The stack draws each cell at section z plus cell z (`sectionModelMatrix`, `src/features/collection/sectionStackModel.ts:123`), and the depth range and hover text add them the same way (`stackDepths` at line 108; `SectionStackViewer.tsx:176`).
  - With two sections 100 µm apart, the second section's cells at 100–102 µm are drawn at 200–202 µm, and the stack spans 0–202 µm.
- **Reproduction:** `evidence/repro/addendum/sections-depth-twice.repro.ts` (records). The control case shows the whole table's cells at their own z.
- **Impact:** the split stack misplaces every section but the shallowest, and hover reports wrong depths. Nothing on screen says so. A table whose third obsm column is the section depth itself, as `docs/host-your-own-data.md` suggests, is not affected, because that z does not vary within a section.
- **Smallest correction:** when a section has a z from `sections()` and its cells keep their own z, store the cells' z relative to the section's (cell z − section z). Share one helper between `sections()` and `withSection` so both compute the same section z.
- **Acceptance:** the repro's second section is drawn at 100–102 µm, and the stack spans 0–102 µm. A case with a constant third column is unchanged.
- **Remaining uncertainty:** whether published multi-section tables have this shape. The EF6 file the commits were checked on was not read.

### EXP-041 A whole-number section column is not found for a split

- Confidence: exec, on anndata-written fixtures (`evidence/fixtures/addendum/`). Status: new. Category: correctness, or documentation if the docs change instead.
- Expected:
  - `collection=<table>` splits by "the first obs column named `section`, `section_id`, … (any case)" (`docs/dataset-collections.md`, Sections Of One Table; also `docs/host-your-own-data.md`).
  - `Open N Sections` is offered for "an obs column named like a section column … of 2 to 500 values" (`docs/ui-reference.md`).
- Actual:
  - anndata writes integer obs columns as plain numeric arrays (`expected.json`: `"section": "array"`), which the reader treats as number tracks (`h5adDataset.ts:3618`).
  - `sectionColumns()` lists label columns only (`h5adDataset.ts:1141-1156`), so the split asks for a column, and its list of candidates leaves `section` out (`annDataSectionCollection.ts:99`).
  - `sectionSplitLink` searches the annotation sets, which are label columns, so no link is shown (`src/features/collection/sectionSplitModel.ts:44`).
  - `#obs.section` splits the same file correctly into 1, 2 and 3, and the string version of the file splits without naming the column.
- Repro: `evidence/repro/addendum/sections-numeric-column.repro.ts` (records; 5 cases).
- Correction: also list numeric obs columns named like section columns, with 2 to 500 distinct finite values, in `sectionColumns()`, and drive the link from `sectionColumns()`. Otherwise, say "label column" in the three pages. Acceptance: `collection=sections-int.h5ad` gives sections 1, 2 and 3 at z 0, 10 and 20, and `Open 3 Sections` is offered. Uncertainty: whether numeric columns named `sample` should count as well (a product decision).

## Checked without a finding

- **Section rows:** a section's cell IDs, coordinates, obs columns, embeddings, matrix reads (by table row), gene values (renumbered) and annotations all come from its own rows. Cell IDs are unique across the table (`uniqueNames`), so sections cannot collide. Unit tests plus reading the code.
- **Shared read and release:** a section holds the table's cached dataset and releases it when disposed or when its read fails, and the table cannot be evicted while held (`datasetFactory.ts` `sectionSource`, `datasetCache.ts`). Reading only.
- **Section scan cost:**
  - Each section scans every table row to find its own, so opening all sections costs one scan per section.
  - At 1,000,000 cells, opening all of 10, 50 and 100 sections took 0.49 s, 1.23 s and 2.16 s in total, about 21–46 ms per section (`evidence/addendum/sections-scan-cost.json`; Node, run on its own).
  - Each section is a separate task, so this is no freeze. Not a finding.
- **Repeated detection:** each section open and each preview repeats the table's detection probes: one HEAD for an `.h5ad`, a few metadata requests for a Zarr store. The data itself is read once. Recorded as "ambiguous" against the docs' "read nothing more" (DOC-ADD-05); not counted by execution.
- **`geneSets=`:** escaping round-trips through `URLSearchParams` as `query=` does. Sets are restored only with the dataset the link names, and IDs are the lowercased name, unique because saving replaces a set of the same name.
- **`cellView` and schemas:** the manifest default, schema enum, parser and share-link writer agree. The collection schema's path pattern allows `#obs.…` fragments, and the parser keeps them (`evidence/repro/addendum/sections-collection-file.repro.ts`).
- **End to end in the built app:** `Open 3 Sections` on `cells3d.h5ad` opened the split collection with sections s0 to s2 and named the tab "s0 · Spatial Omics Explorer". The 3D cell view showed "3,000 cells, z 0 to 101 µm" (`evidence/addendum/new-ui.json`).
