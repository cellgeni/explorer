# Phase 7 — AnnData H5AD

The user asked for `5AD` support; this was read as H5AD. Scope: point-based
cells with per-cell expression and `obs` observations, both categorical and
continuous.

## Product Decisions

- [x] A new `AnnDataH5adDataset` platform, not a branch of Xenium or Visium HD.
      Extend `Platform` and `AppPlatformAdapter`.
- [x] Accept a direct `.h5ad` URL. Do not append Xenium or Visium file names.
      Since 2026-11-14 an AnnData Zarr store opens the same way; see
      [AnnData Zarr Stores](#anndata-zarr-stores-2026-11-14).
- [x] Point-only MVP. No image, boundaries, nuclei, or transcripts; those
      controls are hidden or disabled. Since 2026-11-15 (#114) a collection
      entry or an H5AD manifest can attach an image, and an OME-Zarr label
      mask whose outlines become cell boundaries (see
      [Phase 20](20-dataset-collections.md) and
      [Phase 11](11-dataset-manifest.md#later-additions)).
- [x] Require a 2D coordinate matrix (see [5.3](../data-contracts.md#53-anndata-h5ad)). Never fall
      back to row order.
- [x] Categorical `obs` columns become annotations; numeric and boolean columns
      become continuous tracks and Cell Info fields.
  - [x] **Reopened (2026-11-08), fixed (2026-11-09):** numeric columns
        reach Cell Info ("Observations") and, via `metadataTracks()` at load,
        the `Cell color` → `Metadata` tracks.
  - [x] **Reopened (2026-11-08), fixed (2026-11-09):** boolean columns
        failed on the reference backend and in SpatialData tables; Zarr
        `BoolArray` values now read as 0/1, as on h5wasm.
- [x] `/X` first; `/layers/*` and `/raw/X` later.
- [x] Read remote files through a worker-backed, Range-capable h5wasm reader,
      avoiding full-file fetches except for tiny fixtures or budgeted paths.
      Done 2026-11-17; see [Range Reads](#range-reads-2026-11-17).
- [x] Do not regress Xenium or Visium HD.

## Slices

- [x] 1. Detection and file-URL plumbing.
- [x] 2. Schema reader: groups, encoding attributes, indexes, `obsm` keys,

- [x] 3. Point overview with stable IDs, extent, and observation summaries.
- [x] 4. Observation tracks: lazy `obs` reads, categorical vs continuous,

- [x] 5. Gene panel and expression: selected genes, ROI summaries, and

  - [x] **Reopened (2026-11-08), fixed (2026-11-13):** "worker reads". H5AD
        files up to 300 MiB open in an H5 file worker. Lazy Range reads
        followed on 2026-11-17 ([Range Reads](#range-reads-2026-11-17)).
- [x] 6. Platform adapter and lifecycle: reset, URL state, ROI, selection, and
     overlays per platform.
- [x] 7 (partial). Diagnostics and structured errors for unsupported encodings,
      missing coordinates, missing genes, oversized reads, and HDF5 failures.
- [x] 8 (partial). Tests with tiny h5wasm-generated fixtures, app-level
      regression tests, and a browser smoke test.

## Execution Notes

- H5AD skips the directory-style probes. The factory passes custom fetchers to
  H5AD instances for tests.
- `/obs`, `/var`, `/obsm/X_spatial` or `/obsm/spatial` (falling back to
  embeddings), and dense, CSR, or CSC `/X` are parsed.
- Category sidecars (`/obs/__categories/<column>`) make PBMC-style columns
  categorical.
- Cells render as pickable points with obs IDs, extent fitting, categorical
  annotations, numeric tracks, hover and Cell Info values, gene overlays, ROI
  gene summaries, and selected-cell profiles.
- The Cell tab lists every valid 2D `obsm` matrix as an embedding.
  **Superseded (2026-11-14, #96):** only keys named as embeddings are listed:
  `X_<name>`, or a bare `spatial`, `umap`, `tsne` or `pca`, in any case. A
  cell2location abundance matrix had been offered as an embedding.
- Gating: transcripts, boundaries, nuclei, and transcript Magic Lens are off;
  point ROI, annotations, metadata colouring, and gene expression are on.
- Diagnostics check the H5AD URL instead of Xenium files.
- Size gate, range reads and kerchunk reference: see
  [5.3](../data-contracts.md#53-anndata-h5ad).
- Cell Info shows `obs` values as "Observations" (`6fe02be`, 2026-07-09).
- Imported CSV/JSON annotation files were parsed with the Xenium cell-ID rule
  (`/^[a-p]{8}-\d+$/`), so files keyed by H5AD obs names were rejected. Since
  2026-11-12 any non-empty ID is accepted (`asAnyCellId`) and checked against
  the placed cells: none on the map is an error, some missing a notice.

## Range Reads (2026-11-17)

A plain `.h5ad` over 64 MiB, or of unknown size, is opened by the H5 file
worker from its URL and read by range (`readH5adByRange`), through the range
file and block cache the Xenium H5 fallback and Visium HD already use. Before,
every file up to 300 MiB was downloaded whole on the main thread, and larger
ones needed a companion reference.

- [x] The worker's tree walk visits only `X`, `obs`, `var`, `obsm`,
      `uns/spatial` and `uns/spatialdata_attrs` (`treePaths`). Each object
      visited is an object-header read, so tissue images, `raw`, `layers`,
      the pairwise matrices and the rest of `uns` are never touched.
- [x] `/X` is read whole at load, as from a downloaded file, so Plots and
      gene colouring work as before. Over the 300 MiB size limit, `/X` is
      read whole only if its arrays decode to 300 MiB or less; otherwise it
      is sliced per request (`dense-h5`, `csr-lazy`, `csc-lazy`), and the
      Zarr backends share the sparse kinds. Slices take the request's abort
      signal, so a superseded viewport drops reads still queued for the
      worker.
- [x] `rangeOnly`: a host that ignores Range, or hides the file's size, fails
      the worker's open with `H5RangeUnsupportedError`, and the file is
      downloaded whole within the 300 MiB limit, as before.
- [x] Files up to 64 MiB are still downloaded whole: by range they take 15 to
      25 round trips, mostly to headers spread through the file
      (`H5AD_RANGE_MIN_FILE_BYTES`). Over 300 MiB, the file is now read by
      range instead of refused.
- [x] A custom fetcher (tests) keeps the main-thread download.

Measured from the UK against CELLxGENE's S3 (production build, Chromium with
GPU, 2026-11-17):

| File                      | Before                          | By range                             |
| ------------------------- | ------------------------------- | ------------------------------------ |
| 226 MB Visium heart       | whole download, 16–27 s by curl | ready in 8.8 s; 23 requests, 22.5 MB |
| 333 MB Visium heart       | refused without a companion     | ready in 7.1 s; 22 requests, 12.4 MB |
| hires image of the 226 MB | in the download                 | 6 requests, 4.8 MB, after ready      |

Replayed in Node through the same cache (requests and bytes only), the 14 MB
and 48 MB gallery files took 14 and 19 requests (8.4 and 26.7 MB), slower than
downloading them whole at 200 ms a round trip, hence the 64 MiB floor. The
226 MB heart's `/X` holds 14 MB, and a fullres image in `uns/spatial` that
the viewer never draws holds 183 MB.

Known gaps:

- [x] Plots read a `/X` sliced per request by range too, since merging
      Phase 22 M2: CSR in batches of rows, CSC by column, dense in bands of
      whole cells (`denseH5RowBands`), all under the panel's read budget.
- [ ] Collection previews still refuse a plain `.h5ad` over 64 MiB
      (`PREVIEW_MAX_WHOLE_FILE_BYTES`), though reading one by range may now
      be cheap enough.
- [x] Range reads come before a companion over 300 MiB too (2026-11-17):
      they load the 333 MB heart in 7.1 s, against 37–39 s through its JSON
      reference, and read an `/X` within 300 MiB whole, where the reference
      reads all of a CSR `/X` for every gene (MYH7 25 s). A `.h5ad.json` or
      `.h5ad.icechunk` is read only when the worker cannot open the file by
      range (`H5RangeUnsupportedError`: Range ignored, or the size hidden).
      Not yet measured: a file whose `/X` decodes to over 300 MiB, sliced per
      request by both paths (the reference with 6 reads in flight, the
      worker one at a time).
      ([Large H5AD files](../../h5ad-reference.md)).
- [ ] Diagnose dataset checks Range support but not that the walk stays small.

## AnnData Zarr Stores (2026-11-14)

A store written with `adata.write_zarr` was routed to the OME-Zarr image
loader. Reference store: the hindlimb scRNA-seq atlas (see
[Reference Datasets](../../../PLAN.md#reference-datasets)).

- [x] Detection reads the root attributes once; `encoding-type: anndata`
      opens the AnnData reader (`platform: 'h5ad'`, `source: 'zarr'`) for
      `.zarr` and plain folder URLs. SpatialData is still checked first (#90).
- [x] `src/datasets/annDataZarrStore.ts` uses consolidated metadata when
      present. Otherwise it walks only `X`, `obs`, `var`, `obsm` and
      `uns/spatial`, taking children from encoding attributes, and those of
      `obsm` and `uns/spatial` from the host's listing (S3 ListObjectsV2 or
      an index page) or, without one, the usual embedding names. The
      hindlimb store walks to 110 nodes in 1.2–1.8 s.
- [x] Node names are percent-encoded before zarrita resolves them, so an obs
      column ending in spaces opens; this also fixes SpatialData tables and
      Icechunk AnnData.
- [x] Diagnostics add an `anndata-zarr-store` check that reads the first
      chunk of `/X`.
- [x] Dense Zarr `/X` is read chunk by chunk for cell profiles and ROI gene
      stats, each chunk once for all requested cells (#91). A read whose
      chunks for one cell decode to over 256 MiB
      (`denseCellProfileMaxBytes`) is refused before any request, with
      "Expression matrix chunked by gene" and the `write_zarr` chunks to use.
      The hindlimb `/X` (chunks `[125955, 10]`) would cost 6.1 GB per cell.

Known gaps:

- [ ] Zipped AnnData Zarr is not detected, nor a store written before
      anndata 0.8 (no root `encoding-type`) at a URL that does not end in
      `.zarr`. One at a `.zarr` URL opens by its `obs` dataframe since #170
      (2026-11-18).
- [ ] `matrix()` takes no abort signal, so a profile read within budget
      continues after another cell is clicked.
